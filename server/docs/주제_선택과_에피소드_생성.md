# 주제 선택과 에피소드 생성 (v1.2 백엔드)

## 1. 방송이 시작되는 흐름

```
앱: session.started ─▶ 서버: 주제 선택(TopicSelector)
                         │
                         ├─ 즉시: HOOK "오늘 함께 생각해 볼 질문은 이거예요. {질문}"  (카탈로그, 지연 0)
                         │
                         └─ 백그라운드: 본문 제작(EpisodeProducer)
                              ① 리서처 LLM + 웹 검색  → 근거 브리프
                              ② 코드 검증            → 검색이 실제로 가져온 URL의 사실만 남김
                              ③ 작가 LLM             → FRAME · PERSPECTIVE×3+ · OUTRO 원고
                              ④ 코드 검증            → 출처 없는 숫자·"연구 결과" 문장 삭제, 500자 제한 분할
앱: HOOK 재생 완료 ACK ─▶ 본문 준비됐으면 다음 세그먼트, 아니면 준비되는 순간 서버가 push
마지막 OUTRO 완료 ─▶ 다음 주제를 골라 "다음 이야기로 넘어가 볼게요." 로 이어서 방송
```

- 사용자가 `select_topic` 으로 고르면 그 주제로 바로 바뀐다 (기존 동작 유지).
- 내비 안내로 끊긴 세그먼트(`INTERRUPTED` ACK)는 안내가 끝나면 "이어서 들려드릴게요." 로 다시 재생한다.
- 안내 중에 세그먼트가 끝나면 다음 세그먼트는 안내가 끝날 때까지 보류한다.
- 청취자가 말하면 현재 세그먼트가 끝난 뒤, 다음 세그먼트보다 먼저 답한다.
- 내비 종료를 `navigation.guidance_ended` 대신 `context.updated`(`guidance_active: false`)로만 알려도 똑같이 재개한다.
- 앱이 ACK를 보내지 않으면 (30초 + 글자 수 ÷ 3초) 뒤 다음 이벤트가 올 때 유실로 보고 다음으로 넘어간다. 내비 안내 중에는 이 시간을 세지 않는다.
- 주제를 바꾸면 이전 주제에 대한 대기 중 답변도 버린다.
- 세션 상태는 소켓이 끊길 때가 아니라 `session.ended`에서 지운다 (잠깐 끊겼다 다시 붙는 차를 위해).
- `STORY_SLOT`("다른 청취자 생각도 만나볼게요")은 Story Relay가 생기기 전까지 방송하지 않는다.

## 2. 주제 카탈로그 — `backend/roadpod/data/topics.json`

5개 분류 × 6개 = 30개. 운영자가 JSON만 고쳐서 늘리고 다듬을 수 있다.

| 필드 | 의미 |
|---|---|
| `question` / `summary` | HOOK과 FRAME에 쓰이는 질문과 한 줄 소개 |
| `angles` | 서로 긴장 관계인 관점 2~3개. 작가 LLM이 한쪽 편만 들지 않게 하는 뼈대 |
| `commute_fit` | 출근·퇴근 적합도 0~1 (초기 기본값, 데이터가 쌓이면 이력이 우선) |
| `min_minutes` | 최소 분량. 남은 주행 시간보다 길면 고르지 않음 |
| `fresh_sources` | 시사·사회처럼 최신 자료가 필요한 주제 |
| `sensitivity` | `careful`이면 작가 LLM이 어떤 입장도 지지·비판하지 않도록 추가 지시 |
| `search_hint` | 리서처 LLM의 검색 방향 |

## 3. 주제 고르는 규칙 — `backend/roadpod/topics.py`

1. 최근 14일 안에 들은 주제는 제외 (다 들었으면 반복 허용)
2. 내비 남은 시간(`eta_seconds`)보다 긴 주제 제외
3. 관심 분야(`set_interests`)가 있으면 그 안에서만
4. 25% 확률로 **탐색**: 이번 출퇴근에서 가장 적게 들은 분야에서 고름
5. 나머지 75%는 `출퇴근 적합도 + 0.6 × 분야 선호도` 상위 3개 중 가중 랜덤

분야 선호도는 **출근·퇴근을 따로** 계산한다 (`topic_history`).

| 신호 | 점수 |
|---|---|
| 끝까지 들음 | +1 |
| 방송 중 말을 걸거나 사연을 남김 | +2 (가장 강한 신호) |
| HOOK만 듣고 스킵 | −2 |
| 중간에 스킵 | −1 |

## 4. "자료를 찾아오는 역할" — 리서처와 작가를 나눈 이유

LLM 한 번에 검색과 집필을 다 시키면 그럴듯한 출처를 지어내도 걸러낼 지점이 없다. 그래서 둘 사이에 코드 검증을 둔다.

- **리서처** (`OPENAI_RESEARCH_MODEL`, `web_search` 도구 사용): 사실·통계·사례를 `source_url`, 게시일과 함께 JSON으로 정리
- **검증**: 웹 검색이 실제로 가져온 페이지 목록(`web_search_call` sources)·인용(`url_citation`)과 URL이 일치하는 사실만 남김
  - 블로그·카페·커뮤니티·나무위키 등은 출처에서 제외, 한 출처당 최대 3개, 전체 최대 8개
  - 리서처의 관점 설명(reasoning)은 검증되지 않았으므로 작가에게 넘기지 않음 (관점 제목만 전달)
  - 시사·사회: 2년 이내 날짜가 있고(연도는 방송에서 말로 밝힘), 서로 다른 출처 2곳 이상이어야 사실을 방송에 씀
  - 기준 미달이면 `discussion_only`: 사실 주장 없이 관점과 질문만으로 원고 작성
- **작가** (`OPENAI_WRITER_MODEL`): 브리프에 있는 사실만, `source_refs`로 근거 id를 달고, 말로도 출처를 밝힘
- **원고 검증**: 근거 id 없이 숫자(%·명·억 등)나 "조사에 따르면/연구 결과"가 나오는 세그먼트는 삭제

**캐시**: 브리프는 주제별로 모든 청취자가 공유(시사 12시간, 그 외 30일), 원고는 주제 × 출퇴근별. 같은 주제를 두 차가 동시에 요청하면 제작은 한 번만 한다.

**출처는 서버 DB에만 저장**한다 (`episode_segments.source_refs`, `episode_briefs`). `dj.speak` 계약은 추가 필드를 허용하지 않기 때문이다.

## 5. 친구와 합의할 계약 변경안 (아직 `contracts/`에 반영하지 않음)

| 이벤트 | 지금 서버 동작 | 앱이 해야 할 일 |
|---|---|---|
| `session.started` | 서버가 주제를 골라 HOOK을 보냄 | 세션 연결 직후 한 번 전송 (계약에 이미 있는 이벤트) |
| `user.action` `skip_topic` | 현재 주제 스킵 기록 후 다른 주제 | "다른 얘기 해줘" 음성·버튼 |
| `user.action` `random_topic` | 덜 들은 분야에서 새 주제 | "아무거나" 버튼 |
| `user.action` `set_interests` + `categories: ["MIND", ...]` | 관심 분야 저장, 잘못된 값은 `protocol.error` `INVALID_CATEGORIES` | 첫 실행 온보딩 화면 (주차 중) |
| 서버 발신 `dj.speak` (요청 없이 도착) | 백그라운드 본문이 준비되면 push | 요청하지 않은 `dj.speak`도 큐에 넣어 재생 |
| `command.ack` `INTERRUPTED` | 내비 종료 후 해당 세그먼트 재생 | 안내 때문에 TTS를 멈추면 반드시 `INTERRUPTED` 회신 |

## 6. 아직 안 되는 것

- 실측(gpt-4.1-mini, 2026-11-11): 본문 제작 20~25초, 원고 약 1,700자(약 5분). 6~8분 목표엔 못 미침 → `OPENAI_WRITER_MODEL`에 더 큰 모델 시험 필요
- 첫 청취자는 HOOK 뒤 본문이 올 때까지 10~20초 공백이 생길 수 있음 → 다음 주제 미리 제작(prefetch) 필요
- 심리·관계 주제는 한국어 검색에서 블로그만 나오는 경우가 많아 `discussion_only`(사실 주장 없는 원고)로 자주 떨어짐
- 서버 재시작 시 이력·캐시 유지 (현재 SQLite 메모리 DB)
- 사연 기반 새 주제 발굴, Story Relay(`STORY_SLOT`)
- 다음 주제 미리 제작(prefetch). 지금은 첫 청취자가 본문 제작 시간만큼 기다릴 수 있음
- 출처 없는 주장 필터는 정규식 휴리스틱이라 모든 지어낸 주장을 잡지는 못함 → 운영 전 사람 검수 또는 LLM 팩트체크 단계 필요

## 7. 모델 설정 (2026-11-11 실측 비교)

같은 주제 2개(집중력, 주 4일제)로 세 조합을 비교했다.

| 조합 | 리서치 | 원고 | 분량 | 근거 확보 | 제작 시간 |
|---|---|---|---|---|---|
| A | gpt-4.1-mini | gpt-4.1 | 6.4~7.0분 | 1/2 (한 번은 리서치 출력 파싱 실패) | 24~42초 |
| B | gpt-5.4-mini (effort low) | gpt-5.4-mini (medium, verbosity high) | 5.5~6.8분 | 2/2 | 54~59초 |
| C (채택) | gpt-5.4-mini (effort low) | gpt-5.5 (medium, verbosity high) | 6.3~6.5분 | 2/2 | 45~47초 |

- gpt-5.4-mini 리서치는 영어 검색으로 학술지(Nature Human Behaviour, 실험심리학 학술지 등)와 공공기관 자료를 찾아왔다.
- B와 C의 원고 품질은 비슷하다. 비용을 줄이려면 `OPENAI_WRITER_MODEL=gpt-5.4-mini`.
- 대화 응답(`OPENAI_MODEL`)은 지연 시간 때문에 gpt-4.1-mini 유지.

## 8. 첫 청취 공백 줄이기

- HOOK 뒤 본문이 아직이면 카탈로그 소개 한 줄(bridge)로 메운다.
- 에피소드가 시작되면 다음 주제를 미리 골라 백그라운드에서 제작한다(prefetch). 자동 연결과 `skip_topic`이 이것을 쓴다.
- 그래도 아직 아무도 듣지 않은 주제는 약 40초 공백이 남는다. 운영 전에는 미리 제작해 둔다:

```bash
ROADPOD_DB=roadpod.sqlite PYTHONPATH=backend python -m roadpod.prewarm --all
```

서버도 같은 `ROADPOD_DB`로 띄워야 캐시를 함께 쓴다. 시사 주제는 12시간, 나머지는 30일마다 다시 제작된다.
